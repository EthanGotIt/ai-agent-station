# Parent-Child RAG 升级说明

## 为什么要做 Parent-Child

单纯固定大小切块虽然实现简单，但在知识问答场景里很容易把完整语义切断。尤其当答案需要结合一整段章节背景、约束条件或者多条步骤说明时，小块本身的信息往往不够完整。  
所以在 AI Agent Station 里，RAG 升级的重点不是只把分块做得更细，而是让检索和回答分别使用不同粒度的上下文。

Parent-Child 的核心思路是：导入时先按章节构建父块，再在父块内部切出更小的子块；检索时先命中子块，提高召回精度；回答时再根据 parent_chunk_id 回查父块，把更完整的章节级内容注入模型。  
这样就形成了典型的 Small-to-Big 链路，也就是“检索看 child，回答看 parent”。

## Query Rewrite 和多路召回

为了缓解用户问法和文档表达不一致的问题，系统不会只用一条原始 query 去查，而是会同时保留原始 query、规范化 query 和关键词 query，最多保留三路查询。  
这些 query 会并行走 PGVector 语义召回和 ES BM25 关键词召回两条检索通道，前者负责补语义相近，后者负责命中专有名词、接口名和配置项。

多路召回的对象主要都是 child chunk。这样做的好处是召回粒度足够细，能最大化命中率；而等到召回完成后，再通过 Parent-Child 关系回查父块，就能把碎片化证据重新组织成完整上下文。  
这也是当前版本里 Query Rewrite、多路召回、RRF 和 Small-to-Big 能串起来的关键。

## RRF 融合与证据去重

不同 query、不同通道召回出来的结果会有重叠，如果直接拼接，不仅顺序不稳定，还容易把相同章节内容重复塞给模型。  
因此系统先对 child chunk 结果做 RRF 融合排序，再按 parent 维度做去重，最终只保留得分最高、证据最完整的父块上下文。

最后输出给模型的不只是正文内容，还会带上来源、章节、召回 query 和融合分数，并以 rag_evidence 事件流式输出到前端。  
这样一方面能增强答案的可解释性，另一方面也方便排查召回质量问题，比如是 query 改写不理想，还是某一路检索命中不足。
