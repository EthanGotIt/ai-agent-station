# P4：迁移退款、删除并收敛运行时

## 前置条件

P3 催发货隔离验收通过。先整理退款/删除现有资格规则、授权内容和远端副作用契约。

## 执行

1. 分别将退款、删除迁入 Java Workflow，沿用既有资格，不借迁移变更业务规则。
2. 授权绑定动作、订单、实际参数、操作影响范围及影响资格的事实；删除明确不可逆范围。
3. 仅共享授权、版本 CAS、事务命令创建、Worker 交接和结果投影；资格与结果核验按动作定义。
4. 新 Run 受理成功后，由协调层集中结束当前工具循环，包括截断同批后续模型工具调用。运行时 FIFO 与取消机制不变。
5. Turn 不等待 Worker；命令持久化后释放 Agent 执行。新 Turn 从持久化事项状态回答执行中、成功、失败或待核验。
6. 阻止同一订单未完成写事项产生冲突命令，不影响只读查询。受理成功不等于操作成功。
7. 本期启动后停止剩余工具调用；复合请求的独立只读查询留作后续，不增加请求依赖引擎或自动补跑。

## 验收、回滚、交接

三类写操作补参、授权、拒绝、并发、恢复、幂等和业务状态覆盖测试；同批后续工具不执行；后续对话读取最新状态；未知结果不误报。按动作关闭新路由，已有 Java Run 仍可恢复。通过后转 P5。

## P4 完成证据（2026-09-28）

- `REFUND_JAVA_V1` 与 `DELETE_JAVA_V1` 已由版本路由选择，恢复按持久化编排版本执行；退款原因补参、授权事实指纹、删除范围和资格判断分别由独立策略表达。
- `AGENT_ORDER_WRITE_RESERVATION` 以用户和订单为唯一键，在 WorkflowRun 创建时预留，Worker 核验成功或用户取消/拒绝时释放；重复批准通过 Checkpoint 版本校验和 Command 幂等键收口。
- 协调层在 Workflow Tool 成功启动后截断当前工具批次；Worker 不占用原 Agent Turn，后续 Turn 读取最近 Workflow/Command 状态并明确区分命令受理与业务成功。
