# P2：外部动作结果核验

## 前置条件

P1 通过。查清订单服务幂等回执契约、命令结果存储和夹具能力。

## 执行

1. 区分明确成功、明确失败、结果未知，并将可重试性作为独立属性。
2. 持久化待核验命令/Workflow 状态，贯通数据库、Core、DTO、Item Codec、前端与上下文。
3. 查明订单服务是否支持按幂等身份读取动作回执；没有独立查询接口时，仅在服务端幂等重放契约成立的前提下，以原幂等键重放核验，并由夹具覆盖响应丢失。
4. 超时、断连、远端成功但本地回执失败一律待核验，不新建命令。先查回执；只有契约保证时才以相同幂等键重放。
5. 核验有独立有限退避；耗尽后人工处理，不能把未知改成失败。
6. 为退款、催发货、删除分别定义成功证据。不能仅凭查无订单判定删除成功，不能仅凭订单仍已支付判定催发货成功。

## 验收、回滚、交接

注入响应丢失、进程崩溃、Lease 过期、多 Worker 后业务变更至多一次。核验不可用时 UI 与后续 Agent 均显示待核实；明确失败与未知有不同恢复路径。迁移只增不删；回滚应用须认识新状态。完成后转 P3。

## P2 执行证据（2026-09-24）

- Core 将动作结果区分为 `PENDING`、`SUCCEEDED`、`FAILED`、`UNKNOWN`；未知结果进入独立有限核验预算，耗尽后保持待人工核验，人工操作沿用原命令和幂等键。
- HTTP 超时、服务端错误、连接异常及动作成功后的本地回执异常不会伪装成明确失败。删除成功只接受明确动作回执；查不到订单不作为成功证明。
- 本订单服务契约没有独立的按幂等键查询 API，因此 Worker 使用相同幂等键重放。隔离订单夹具以 `COMMIT_THEN_ERROR` 模拟远端已提交、响应丢失；回放取回缓存回执且业务变更次数保持一次。其他订单服务必须先确认同等服务端幂等保证。
- 状态已贯通 MySQL V13、Items、Workflow 结果、上下文和前端；旧 V9 数据迁移及新核验状态 round-trip 已用隔离 MySQL 验证。
- 验证：Core 99 项、Infrastructure 145 项、HTTP 集成 9 项、App 单测 25 项；MySQL acceptance 两个套件共 10 项通过。Python 27 项、前端 typecheck、Vitest 77 项、production build、`convention_check` 和 `git diff --check` 通过。此前全量 reactor 首次执行中的两个测试夹具错误已修复，并单独重跑两个 MySQL acceptance 套件通过；未因此宣称真实第三方订单服务、浏览器或 Live 模型已验收。
